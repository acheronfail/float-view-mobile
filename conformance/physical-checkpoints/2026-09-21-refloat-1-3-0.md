# Refloat 1.3.0 physical checkpoint

Date: 2026-09-21

Status: canonical ESP32 physical checkpoint complete; task 5.3 is complete.

The connected ESP32 runs the canonical serial-controlled BLE byte bridge with
source-derived Refloat 1.3.0 simulation. This is physical transport evidence,
not evidence from a motor controller running the actual Refloat package.

Available targets: development iPhone 12, Android SM-G965F, and local macOS.

## Issues found during the checkpoint

- iOS initially could not build because Xcode had no signed-in account/profile.
  The user signed in and trusted the developer profile on the iPhone.
- The 1.3.0 control fixtures retained a 1.2.3 identity field. Corrected identity
  metadata and added explicit 1.3.0 selection for ride/reconnect/background.
- The simulator did not treat command 33 as live telemetry, so it encoded idle
  state rather than the selected source and control state. Corrected both paths
  and added state-transition regression coverage, including the fatal latch.
- The first Android run passed direct controls but failed CAN control confirmation.
  Inspection found that slow/fault requests could starve fast state at idle
  polling intervals. Fast polls now precede due probes on one scheduler lane;
  focused Rust tests and the complete Rust lint/test gates passed.
- The existing configuration checkpoint did not restore its original values.
  Added restore and complete readback verification. This exposed the simulator's
  write allowlist rejecting restoration, then its missing firmware normalization.
  Restoration now preserves original values with the source-defined clearing of
  `meta.is_default`; both fixture behavior and assertions cover this explicitly.

## Runs

Corrected iOS run passed all six selected scenarios: `control-direct`,
`control-can`, `direct`, `ride`, `unexpected-disconnect`, and `background`.
Both configuration routes verified restoration with firmware metadata
normalization. Controls included package, lighting, flywheel, and fatal clear.
Ride exercised session retrieval and CSV export. Background recovery retained
BLE telemetry and session growth. Location was authorized/available; persisted
location rows and committed sequence stayed at 2 during the dwell (no new
background fix observed), so this does not claim new background location data.
Application, proxy, lifecycle-runner, and fixture cleanup completed.

Android passed all 17 canonical scenarios across three completed portions:
identity/direct/legacy and both control/configuration routes; all shutdown,
explicit-CAN, generic-gateway, and ambiguous-selection scenarios; and all BMS,
ride, reconnect, and background scenarios. Background location was
`authorized/available`, with rows/sequence unchanged at 1 during the dwell;
new background location acquisition remains unverified. The Android session-review/export exclusion was removed. Ride followed by
background passed with the same session retrieval, series query, CSV export,
and deletion assertions used on Apple. An initial export-to-background run
exposed a test-adapter cleanup issue: force-stopping the app while the system
chooser requested its FileProvider led Android to terminate the next process
for a provider-publication timeout. The adapter now dismisses the resumed system
chooser first; the combined ride/background rerun passed and the device returned
to its launcher. An ESP32 asynchronous reset/advertising race was reproduced and a
bounded startup-only retry added (three retries, persistent failure still fails).
A simultaneous Android software run reused the physical adapter's host port and
interrupted BMS testing; the interrupted scenario passed when rerun sequentially.

macOS passed all 16 canonical physical scenarios in one corrected run, including
ride/session retrieval/CSV export and complete cleanup. iOS also passed the
remaining 11 identity/legacy/shutdown/routing/BMS scenarios, completing its full
17-scenario matrix. Android completed all 17 scenarios across the portions
above, plus the strengthened ride/background/export rerun.

All runners reset the ESP32 and turned off its status LED. Mobile applications,

This checkpoint does not claim new background GPS fixes: both phones had
available authorization, but no new location rows arrived during their brief
background dwell. It also does not claim tests on a real motor controller.

## Software validation

Rust formatting, warnings-denied lint, all Rust tests, all 185 conformance
regression tests and type checks, and strict OpenSpec validation passed. All stages
of `just verify` passed across its run and continuation: the final Android
software stage initially lacked a running emulator, then hit insufficient
emulator storage. Removing the disposable test installation allowed Android
software conformance to pass; the final `just audit` also passed. The full command
was not a single uninterrupted successful invocation.

Select the audited package with `FLOAT_VIEW_PHYSICAL_REFLOAT_VERSION=1.3.0`
and run `just conformance-physical <platform> <fixture-port> [device-id]`.
Legacy and standalone BMS scenarios keep their original identities.
