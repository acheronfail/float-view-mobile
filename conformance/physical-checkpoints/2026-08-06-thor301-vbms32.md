# Thor301 with VBMS32 physical checkpoint

Date: 2026-08-06  
Topology: direct BLE Thor301 motor controller plus CAN-routed VBMS32  
Board name: `Thor301`

## Retained bounded identity

The native auxiliary scan observed two CAN nodes:

| CAN ID | Hardware name | Hardware type                 | Wire version | Role             |
| ------ | ------------- | ----------------------------- | ------------ | ---------------- |
| 3      | `Thor301`     | `0` (`HW_TYPE_VESC`)          | 6.06         | motor controller |
| 10     | `VBMS32`      | `2` (`HW_TYPE_CUSTOM_MODULE`) | 6.06         | BMS              |

CAN ID `10` is route configuration, not VBMS32 product identity. VESC Express
persists its configurable controller ID; upstream commit
`e07a098d3af2c72f1873ad833821f8b548627063` changed the VBMS32 default to `3`.
The observed board therefore uses a distinct persisted ID to coexist with the
Thor301 controller at CAN ID `3`. The evidence does not establish whether the
manufacturer or a later configuration selected `10`.

## Upstream correlation

- VESC Express commit `a9f496c48107ae507b2303157683843f3bbf236c`, the last
  6.06 revision before the 7.00 version bump, emits
  `HW_TYPE_CUSTOM_MODULE` from `main/commands.c` and `main/comm_can.c`.
- `main/hwconf/vesc/vbms32/hw_vbms32.h` defines hardware name `VBMS32`.
- `main/commands.c` routes `COMM_BMS_GET_VALUES` to `main/bms.c`.
- The corresponding immutable identity vector is
  `backends/fixtures/vesc-bms/source-derived.json` case
  `vbms32-firmware-6.06`.

## Compatibility conclusion

Float View supports the exact tuple `VBMS32`, hardware type `2`, version 6.06
in addition to stock VESC BMS 6.00/type 1. It does not treat arbitrary custom
modules as BMS devices. VESC Express 7.00 remains fail-closed until separately
audited and physically verified.
